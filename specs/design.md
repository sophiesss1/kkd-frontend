# Дизайн решения

## Модель данных (фронтенд)

Типы контракта — `src/api/types.ts`, повторяют ответы mock API. Ключевое про nullability:

- `Metric.previous`, `delta`, `delta_pct`, `trend` — `null` в первом прогоне; `value` — `null`, если в подразделении нет целей.
- `Metric.trend` у нейтральной метрики (`higher_is_better: null`, например «Активные цели») — `null`, если она
  изменилась, и `same` при нулевой дельте.
- `Summary.compared_to` и все `summary.delta.*` — `null` при отсутствии предыдущего успешного прогона.
- `Issue.delta_status` — `new | persisting | resolved`; исправленные приходят только при `delta_status=resolved`.

## API

| Запрос | Где используется | Кэш |
|---|---|---|
| `GET /api/meta` | дерево подразделений, справочник правил, подписи важности, статусов и уровней целей | `staleTime: Infinity` |
| `GET /api/runs?limit=100` | выбор прогона, плашка сравнения, причина ошибки прогона | 60 с |
| `GET /api/kkd/summary?run_id&unit_id` | метрики, разбивки, счётчики дельты | ключ `[summary, run, unit]` |
| `GET /api/kkd/issues?...` | таблица | ключ включает все фильтры и страницу |
| `GET /api/kkd/issues/{id}?run_id` | карточка проблемы | ключ `[issue, id, run]` |
| `GET /api/kkd/units?run_id` | «Где стало хуже», оговорка к итогу, окно «Все подразделения» | ключ `[units, run]`: от подразделения не зависит, один запрос на прогон; не шлётся для неуспешного прогона и для подразделения без дочерних |
| `GET /api/kkd/trend?unit_id&metric&limit=8` | динамика главной метрики | ключ `[trend, unit, metric]` |
| `GET /api/kkd/issues/export?...` | кнопка «Выгрузить CSV» | не кэшируется: обычная ссылка с теми же фильтрами, что у списка, файл отдаёт API |

Все ключи — в `queryKeys` (`src/api/queries.ts`), поэтому повторные обращения из разных компонентов берутся из кэша.
4xx не ретраятся (это ответ по существу: 404, 409, 422), сетевые ошибки и 5xx — до 2 повторов.

`run_id` всегда передаётся явным идентификатором: `latest` не используется, чтобы выбранное значение в селекте
и данные на экране гарантированно совпадали. По умолчанию берётся первый `completed` из `GET /api/runs`.
Если прогона из ссылки нет в первых 100 из `GET /api/runs`, об успехе прогона и о сравнении судим по сводке.
Нет ни одного успешного прогона — сообщение об этом, а не бесконечная загрузка.

Успешный ответ не в JSON (адрес API указывает на что-то другое) клиент превращает в ошибку `INVALID_RESPONSE`
с понятным текстом. «Повторить» в любом блоке перезапрашивает все упавшие запросы страницы (`useRetryFailed`),
а не только свой: при сбое API падают сразу несколько блоков. Страница целиком заменяется ошибкой, только пока
справочников и списка прогонов нет совсем. У разреза `staleTime: Infinity`: результаты успешного прогона
не меняются, а без этого возврат из подразделения без дочерних (там запрос выключен) через минуту запросил бы
разрез заново.

## Ключевые решения

1. **Иерархия информации.** Сверху вниз: контекст (что и с чем сравниваем) → вердикт по главной метрике
   «Доля корректных целей» → ключевые метрики → изменения и разбивка по важности → «что исправить в первую очередь» →
   полный список. Объёмные метрики (число целей, КР) вынесены в строку под карточками — они нейтральны.
2. **Честность дельты.** `DeltaIndicator` получает `trend` из API и не выводит оценку из знака. Для процентных метрик
   разница подписана «п.п.». `null` → «нет данных для сравнения», никогда не 0. Для счётчиков проблем и доли
   в разрезе по подразделениям API не отдаёт `trend`: оценку даёт `trendFromDirection` по `higher_is_better` метрики
   из `GET /api/meta`, само число дельты берётся из API.
3. **Первый прогон.** Статус «Новая» у всех проблем первого прогона был бы неправдой — колонка статуса показывает «—»,
   фильтр статуса отключён. Если статус остался в URL от другого прогона, он не уходит ни в список, ни в выгрузку:
   иначе таблица показала бы «проблем нет» с фильтром, который нельзя снять.
4. **Неуспешный прогон.** Ошибку 409 `RUN_FAILED` показываем экраном с причиной (`run.error` из списка прогонов)
   и переходом на последний успешный. Таблицу для такого прогона не запрашиваем.
5. **Состояние в URL** (`useKkdParams` на `useSyncExternalStore` + History API) вместо роутера: одна страница,
   нужна только query-строка. Смена подразделения/прогона сбрасывает пагинацию и закрывает карточку, фильтры сохраняет.
   Поиск добавляет в историю одну запись, а уточнения до ухода из поля её заменяют: «назад» возвращает состояние
   до поиска, а не каждую букву. Заменять или добавлять, решается в момент набора: уточнение, набранное перед
   уходом из поля, всё равно заменяет запись, а следующий заход в поле добавляет свою. Страница за концом списка (старая ссылка с `?page=`) заменяется последней.
   Признак «есть сравнение» берётся из `compared_to_run_id` выбранного прогона, а не из сводки: пока сводка
   нового прогона грузится, на экране ещё прошлая. Повторный клик по уже выбранному адрес не меняет и запись
   в историю не добавляет; у показанного столбца динамики клик ничего не делает (иначе адрес `/` стал бы
   `?run=RUN-008` с тем же содержимым и сбросом страницы списка). Ссылку не доверяем: неизвестные коды важности и статуса и размер страницы вне
   10/20/50/100 отбрасываются при разборе, правила вне справочника — перед запросом (иначе API ответил бы 422).
   Клик по счётчику, строке важности или правилу ставит ровно этот фильтр, остальные сбрасывает. «Сбросить
   фильтры» пересоздаёт поле поиска, и набранный, но ещё не отправленный текст не применится после сброса.
6. **Загрузка.** Первая загрузка — скелетоны. При смене параметров (`keepPreviousData`) прошлые данные остаются,
   но приглушены и помечены «Обновляем данные…», чтобы не выдать старые числа за новые.
7. **Тема и кит.** Задание оценивает визуал по `UI-KIT.md`, поэтому кит главнее этой спецификации: где кит говорит
   прямо, делаем как в ките. Тема из раздела 1 скопирована целиком. Добавлены только значения из самого кита:
   семантические фоны/тексты из раздела 2, у `Modal` — радиус 28px и межстрочный заголовка 28px из разделов 3–4.
   - **Из темы, а не числами** (вступление кита: «тяните цвета и размеры из темы»): включён `cssVar`, и CSS-модули
     берут цвета, размеры шрифтов, межстрочные интервалы, жирность 600 (`fontWeightStrong`) и радиусы
     из `var(--ant-*)`. Карточки — `borderRadiusLG` темы (8px, в ките карточки 8–16px). Внутри модалки
     `borderRadiusLG` переопределён до 28px (радиус окна), поэтому плашки в карточке проблемы — базовый
     `borderRadius` (6px). Все заголовки, включая заголовки карточек и разделов модалки, — 20/600/28
     (`fontSizeHeading4`/`lineHeightHeading4`): в разделе 3 кита других ролей заголовков нет. Подписи 12px —
     `fontSizeSM`/`lineHeightSM` (20px). Числами остались отступы по шкале кита 4–40 (в теме кита их нет), ширины
     полей, рамки, радиус 20px у плашки-пилюли (раздел 4, токена нет) и жирность 500 и 400 (токенов для них нет).
   - **Подсказки** — серые цвета кита (`#90928d`, текст `#e4e6e2`). Строка кита `Tooltip: { colorText, colorBgBase }`
     в antd 5 не действует: подсказку красят `colorBgSpotlight` и `colorTextLightSolid`. Поэтому те же цвета кита
     продублированы в этих токенах. Контраст этой пары — около 2,5:1, это свойство самого кита. Содержимое
     подсказок (формула, значение прогона) дублируется в имени элемента для экранного диктора.
   - **Тона текста.** Раздел 5 кита — «подсказка, а не обязательная часть»; в разделе 2 у каждой роли есть
     отдельный тон для текста. Поэтому слово в теге важности и дельта «лучше / хуже» окрашены текстовым тоном
     роли (`colorWarningText`, `colorErrorText`, `colorSuccessText`), а фон тега — фоном роли. Основной жёлтый
     `#faad14` на `#fffbe6` дал бы 1,8:1, текстовый `#ca820e` — 3:1, темнее жёлтого в ките нет. «Нет данных
     для сравнения» — `colorTextTertiary`, как прямо сказано в разделе 5. Содержательный текст (`Не назначен`,
     даты, в том числе в списке прогонов, «было …») и подписи полей в карточке проблемы — `colorTextSecondary`
     («вторичный текст, подписи» в разделе 2): `Typography type="secondary"` и подписи `Descriptions` в antd 5
     дали бы третичный. По той же причине в теме `colorTextDescription` (пояснения `Result`, `Empty`, хлебные
     крошки) и `colorTextPlaceholder` (подсказки в пустых фильтрах и поиске) — вторичный цвет кита: antd по
     умолчанию даёт 2,7:1 и 1,8:1, а по подсказке фильтра видно, что сейчас выбрано. Оговорка «но хуже в N
     подразделениях» — основным текстом на фоне Warning со значком текстового тона: жёлтый текст давал бы 3:1.
     Экраны «результатов нет» (упавший прогон, неизвестное подразделение) — на карточке, как пустое подразделение:
     на фоне страницы вторичный текст даёт 4,3:1, на карточке — 4,7:1.
   - **Строки таблицы.** Раздел 5 советует строку «под контрол 32px». В ячейках две строки (название и детали
     проблемы, цель и КР), поэтому строка выше; таблица — `size="middle"` antd. Теги — бейджи (так их называет
     раздел 5) с радиусом antd, а не «чипы» с радиусом 20px.
8. **API-адрес.** Клиент обращается к относительному `/api`; nginx (Docker) и Vite (dev) проксируют на `API_URL`.
   nginx ждёт соединения с API не дольше 3 с: остановленный mock API не отвечает на соединение, и без ограничения
   ошибка появлялась через 1–2 минуты (до ~40 с на каждую из трёх попыток), теперь — примерно через 12 с.
   В `.env.example` `API_URL` закомментирован: если скопировать файл в `.env`, его прочитают и Vite, и Docker
   Compose, а адреса у них разные — `localhost:8000` для `npm run dev` и `mock-api:8000` из контейнера.
   Завершающий слэш в `API_URL` снимает `nginx/05-trim-api-url.envsh` (иначе `proxy_pass` отрезал бы `/api/`).
   nginx передаёт API его собственный `Host` и SNI, как `changeOrigin` у Vite, — так работает и внешний https-адрес.
   Ответы сжимаются gzip с `Vary: Accept-Encoding`. `VITE_API_BASE_URL` подставляется в бандл при сборке; в Docker передаётся аргументом
   сборки из compose. `.env.*` (кроме `.env.example`) не попадают ни в git, ни в образ.
9. **Разрез по подразделениям.** Итог по блоку скрывает провалы внутри: в `RUN-008` у `B2B` +0,8 п.п., а у `CIB-REG`
   −25,5 п.п. (гипотеза H1 в `research/03-hypotheses.md`). Поэтому рядом с вердиктом — «Где стало хуже» из
   `GET /api/kkd/units`: необязательный эндпоинт, но один запрос на прогон вместо N запросов `summary`. Сортировка
   по дельте — порядок показа, а не пересчёт. В первом прогоне сверху наименьшие доли. У подразделения без дочерних
   блока нет, на его месте ключевые метрики.
10. **Оговорка к итогу** — только про подразделения, текстом и значком: «но хуже в N подразделениях, сильнее всего — X».
    N — число вложенных подразделений любой глубины, у которых доля корректных целей в `GET /api/kkd/units` снизилась.
    Департамент и его управление считаются по отдельности: у каждого своя доля из API. Так же считаются строка
    «улучшились · без изменений · без целей» и «ни в одном из N вложенных». Это счёт строк ответа по знаку дельты
    из API, метрики при этом не пересчитываются.
11. **Выгрузка CSV** — ссылка на `/api/kkd/issues/export` с теми же фильтрами, что у списка. Кнопка выключена, пока
    список грузится или на экране ещё прошлые данные: иначе выгрузка ушла бы по фильтрам, которых таблица пока не показывает.
12. **Ошибки 422 FastAPI.** Валидация mock API отвечает не в едином формате, а `{"detail": [...]}`; клиент превращает
    это в `INVALID_PARAM` «Некорректные параметры запроса: limit.».
13. **Mock API в compose** собирается из `mock-api/Dockerfile`, который забирает код репозитория задания через `ADD`
    по адресу git. Адрес git прямо в `build:` Docker Compose 5 на Windows передаёт сборщику как путь к папке и падает
    с «failed to execute bake». Коммит зафиксирован (`e6a7431`, голова `master` на 03.11.2026): новая версия mock API
    не изменит числа, на которые опираются README, критерии приёмки и снимок для тестов.
14. **Справочники из `/api/meta`.** Подписи важности, статусов дельты, уровней целей и порядок важности берутся
    из ответа `GET /api/meta` через `DictionariesProvider` (`src/shared/dictionaries.tsx`), а не копией в коде.
    Страница рендерит содержимое только после загрузки meta, поэтому подписи не мигают. Уровень цели в карточке —
    отдельной строкой, подписью из API как есть. Заголовки счётчиков «Новые / Сохраняются / Исправлены» —
    текст интерфейса во множественном числе с пояснением, а не справочник (в API — «Новая», «Сохраняется»);
    набор и порядок счётчиков — по справочнику статусов.
15. **Доступность.** У кнопок со сложным содержимым (строки важности, счётчики, подразделения в разрезе) нет
    `aria-label`: имя для экранного диктора — видимое содержимое, включая дельту и числа, плюс скрытое «показать /
    открыть» (`VisuallyHidden`). У `DeltaIndicator` тоже нет `aria-label` (на `span` без роли он запрещён):
    читается видимый текст. Значки antd по умолчанию озвучиваются по-английски, поэтому: свои значки в кнопках
    скрыты; у кнопок поиска, очистки поиска, закрытия окон и стрелок пагинации — русские имена; значки в сообщениях
    об ошибке (`Alert`, `Result`) скрыты. Заголовок модального окна — `h2` (`ModalTitle`), разделы внутри — `h3`.
    Подсказки (формула, столбцы динамики, «Выгрузить CSV») открываются и по фокусу.

Основание решений 9–11 — исследование в `research/`: план изучения, находки на данных mock API, гипотезы и план решения.

## Изменения по ходу работы

- Карточка «Найдено проблем» перенесена из сетки метрик в блок «Проблемы по важности» как итог разбивки — так сетка
  ключевых метрик ровная (главная + 4), а общее число стоит рядом со своей детализацией.
- По итогам исследования (`research/04-solution-plan.md`) добавлены разрез по подразделениям, оговорка к итогу и
  выгрузка CSV. Блок «Итоги» перестроен: с разрезом итог и «Где стало хуже» стоят рядом, ключевые метрики — строкой ниже.
- Направление «лучше / хуже» для счётчиков проблем больше не константа «меньше — лучше», а берётся из `/api/meta`.
- Mock API в `docker-compose.yml` собирается из локального `mock-api/Dockerfile`, а не прямо по адресу git (решение 13).
- Кнопка CSV выключается и на время смены фильтров, а не только до первой загрузки (решение 11).
- После проверки в браузере на 1280 px окно «Все подразделения» расширено до 1200 px, чтобы самое длинное название
  не переносилось. Строка под названием в «Где стало хуже» теперь переносится, а не обрезается: иначе пропадало число
  критичных.
- По итогам ревью: название проблемы в таблице и подразделения в окне «Все подразделения» — кнопки (`LinkButton`),
  а не `Typography.Link` без `href`, который не получал фокус с клавиатуры. Фильтр статуса в первом прогоне не
  применяется (решение 3), у прокси nginx ограничено время соединения, `.env.example` больше не ломает compose
  (решение 8).
- Сверка с UI-KIT.md по замерам в браузере: главное число 30px вместо 38 (в ките крупные числа 24–30), у заголовка
  модалки межстрочный 28px (`titleLineHeight` в теме, без него antd даёт 30), отступы 2, 5 и 6px заменены на 4.
  nginx отдаёт `index.html` с `Cache-Control: no-cache`: после пересборки браузер показывал старую версию страницы.
- По итогам финального ревью и сверки с заданием:
  - прошлое значение показано и у объёмных метрик, и у «всего проблем» (раньше — только в карточках);
  - ошибка динамики по прогонам показывается с кнопкой «Повторить», а не скрывает блок;
  - поиск и страница за концом списка ведут себя по решению 5, признак сравнения — из списка прогонов;
  - тег «Существенная» читается (решение 7);
  - рекомендации в «Что исправить в первую очередь» переносятся, а не обрезаются;
  - подсказки с формулой и столбцы динамики открываются и с клавиатуры;
  - плашка сравнения пишет «с ошибкой» только у прогонов со статусом `failed`.
- По остальным находкам ревью и сверки:
  - кит выше спецификации: подсказки получили цвета кита, размеры и радиусы — из переменных темы, карточки — 8px
    вместо 12px (решение 7);
  - справочники из `/api/meta` (решение 14), доступные имена кнопок и заголовки модалок (решение 15);
  - разбор ссылки, повторные клики, сброс поиска (решение 5); ошибки, повтор и пустой список прогонов (раздел API);
  - разрез не запрашивается для подразделения без дочерних; фильтры на 1280 px в одну строку, отступ перед таблицей
    есть и без подсказки; под названием подразделения сказано, что метрики — с учётом вложенных;
  - nginx: Host и SNI API, gzip, слэш в `API_URL`; коммит mock API зафиксирован (решения 8 и 13);
