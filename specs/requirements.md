# Требования: страница модуля ККД

## Цель

Руководитель или администратор с первого взгляда понимает две вещи:
1. стало лучше или хуже по сравнению с прошлым прогоном;
2. что исправлять в первую очередь.

## Функциональные требования

| ID | Требование | Источник данных |
|---|---|---|
| F1 | Выбор подразделения (иерархия по `parent_id`) и прогона влияет на всю страницу | `GET /api/meta`, `GET /api/runs` |
| F2 | По умолчанию открыт последний успешный прогон и подразделение `B2B` | `GET /api/runs` |
| F3 | Явно показано, с каким прогоном идёт сравнение (`compared_to_run_id`); если между ними пропущен неуспешный прогон — это написано | `GET /api/runs` |
| F4 | Карточки метрик: значение, прошлое значение, дельта, оценка «лучше / хуже» из `trend` | `GET /api/kkd/summary` |
| F5 | Счётчики new / persisting / resolved кликабельны и открывают список проблем с этим фильтром | `summary.delta` |
| F6 | Разбивка проблем по важности с дельтой; клик открывает список с фильтром | `summary.issues_by_severity` |
| F7 | Блок «Что исправить в первую очередь» — правила с нарушениями: важность ↓, количество ↓ | `summary.issues_by_rule` |
| F8 | Таблица проблем: фильтры по правилу, важности, статусу дельты, поиск, сортировка, серверная пагинация | `GET /api/kkd/issues` |
| F9 | Карточка проблемы в модальном окне: описание, факт и ожидание, рекомендация, история по прогонам | `GET /api/kkd/issues/{id}` |
| F10 | Состояние страницы (подразделение, прогон, фильтры, страница, открытая карточка) хранится в URL | — |

## Нефункциональные требования

- Числа и дельты не пересчитываются на фронтенде — выводятся из ответов API как есть.
- Цвет не единственный носитель смысла: у важности — значок и слово, у дельты — стрелка, знак и слово.
- Визуал — по `UI-KIT.md`: тема antd из справочника, цвета только из темы/CSS-переменных, текст 14/22,
  заголовки 20/600/28, контролы 32px, карточки с радиусом 12px, модалка 28px, отступы кратны 4.
- Десктоп от 1280px. Семантическая разметка: `header`, `main`, `section` с заголовками, списки, кнопки для кликабельных счётчиков.
- Адрес API — в переменной окружения. Запуск — `docker compose up`.
- Одинаковые запросы не дублируются (общий кэш React Query с единой фабрикой ключей).

## Критерии приёмки

| # | Дано / Когда | Тогда |
|---|---|---|
| A1 | Открыт `RUN-001` | Вместо дельт — «нет данных для сравнения», статусы дельты в таблице и фильтр статуса отключены |
| A2 | Выбран `RUN-006` | Показано «Прогон RUN-006 завершился с ошибкой» с причиной и кнопкой перехода на последний успешный прогон; страница не ломается |
| A3 | Выбрано `TX-NEW` | Пустое состояние «нет активных целей», нули не выдаются за метрики |
| A4 | Выбрано `CIB-REG`, последний прогон | Главная карточка «Стало хуже», доля корректных целей упала, в приоритетах — каскадные правила |
| A5 | Открыт `RUN-007` | Плашка: сравнение с `RUN-005`, `RUN-006` пропущен из-за ошибки |
| A6 | Клик по «Исправлены» | Таблица отфильтрована по `delta_status=resolved`, страница прокручена к списку |
| A7 | Фильтр без результатов | «По выбранным фильтрам проблем нет» и кнопка сброса |
| A8 | Mock API недоступен | Сообщение об ошибке сети с кнопкой «Повторить» |
| A9 | Смена подразделения/прогона/фильтра | Без перезагрузки страницы, URL обновлён, «назад» возвращает прошлое состояние |
| A10 | Рост числа проблем | Помечается «хуже» (красный + стрелка вверх + слово), рост доли корректных целей — «лучше» |
