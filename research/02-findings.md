# Результаты изучения

Факты по вопросам из плана (`01-research-plan.md`). Данные — живой mock API, «сегодня» 02.11.2026,
последний прогон RUN-008. Числа зависят от даты запуска, структура датасета фиксирована.

## Q1. Пользователи и их решения

| Роль (БТ, задания BA/Frontend) | Уровень оргструктуры | Решение по итогам проверки |
|---|---|---|
| Бизнес-администратор системы | весь блок B2B | Где качество просело, каким департаментам/подразделениям дать сигнал |
| Руководитель департамента / штаба | департамент (`hq`) | **Какие проблемы поручить исправить и к какому сроку**, чтобы к следующей проверке стало лучше (user story из задания BA) |
| Ответственный за целеполагание в подразделении | подразделение (`unit`) | Какие конкретно цели/КР исправить в модуле «Цели» и как |

- Проверка еженедельная, по понедельникам. Цикл (задание BA): проверка → просмотр результатов → исправление
  в системе целей → следующая проверка. Срок исправления естественным образом — следующий прогон.
- Пользователь — руководитель, а не аналитик: ему нужен вывод, а не набор из 9 метрик.

## Q2. «Стало лучше / хуже»

- Метрики и направление задаёт API (`/api/meta`): `higher_is_better` = true у долей (`clean_goals_share`,
  `cascade_coverage`, `kr_completeness`), false у счётчиков проблем, null у объёмов (`goals_active`, `key_results`,
  `avg_kr_per_goal`) — у них `trend: null`, оценки нет.
- `clean_goals_share` — первая метрика в API, пример в README и в задании Backend; самая интегральная
  (цель «корректна», если по ней и её КР нет ни одной проблемы).
- **Метрики противоречат друг другу.** B2B, RUN-008: доля корректных +0,8 п.п. (лучше), покрытие каскадом −4,3 п.п. (хуже),
  проблем 61 → 61 (без изменений). Одного слова «лучше» недостаточно.

## Q3. «Что исправлять в первую очередь»

- Критичных проблем мало (4 из 61), и **3 из 4 висят все 7 прогонов подряд** (с RUN-001) — их никто не исправляет.
- 25 из 61 проблемы держатся 7 прогонов, 13 — новые. Возраст (`runs_in_row`, `first_detected_at`) — сильный сигнал
  для эскалации; в API есть сортировка `sort=age`.
- Рост по правилам (RUN-008 vs RUN-007): `CASCADE_NO_PARENT` +4, `CASCADE_WRONG_LEVEL` +4 — это причина
  ухудшения (реорганизация CIB-REG). Остальные правила стабильны или снижаются.
- Кому поручить: для руководителя — подразделению (9 подразделений с проблемами, от 1 до 18 проблем);
  для ответственного — владельцу цели. У 6 проблем владельца нет (это само по себе критичное правило `GOAL_NO_OWNER`).
- Проблемы распределены по целям ровно: из 46 целей с проблемами у 34 одна проблема, максимум 4 (цель-«витрина»
  G-00021). Группировка по целям ценности почти не добавляет.
- В каждой проблеме есть `recommendation` (как исправить), `details`, `actual`/`expected`.

## Q4. Каскад и агрегирование

Метрика подразделения = подразделение + все дочерние. **Агрегат скрывает провалы:**

| Подразделение | Доля корректных | Дельта | Оценка |
|---|---|---|---|
| B2B (блок) | 75,8 % | +0,8 п.п. | лучше |
| └ HQ-CIB | 56,5 % | −6,2 п.п. | хуже |
| &nbsp;&nbsp;└ CIB-REG | 36,4 % | **−25,5 п.п.** | хуже |
| &nbsp;&nbsp;└ CIB-KEY | 59,1 % | −2,8 п.п. | хуже |
| └ HQ-TX | 80,9 % | −2,1 п.п. | хуже |
| &nbsp;&nbsp;└ TX-ACQ | 63,6 % | −4,6 п.п. | хуже |
| └ HQ-SME | 89,9 % | +10,2 п.п. | лучше |

Руководитель блока на экране по умолчанию видит «Стало лучше», хотя одно управление потеряло четверть корректных целей.
Готовый разрез даёт `GET /api/kkd/units?run_id` (по каждому подразделению: доля и её дельта, новые/исправленные,
критичные, число целей). Эндпоинт необязательный, но отвечает на Q2 и Q3 точнее обязательных.

## Q5. Дельта

- «Та же» проблема = то же правило + тот же объект (стабильный `id` между прогонами; задания SA и Backend).
- Сравнение — с **предыдущим успешным** прогоном: RUN-007 сравнивается с RUN-005, RUN-006 упал.
- Первый прогон (RUN-001): `compared_to: null`, все `previous`/`delta`/`trend` = null, счётчики `delta.*` = null,
  **у всех 54 проблем `delta_status: "new"` и `runs_in_row: 1`** — показывать их как «новые» было бы неправдой.
- **Нетто-дельта скрывает оборот:** проблем 61 → 61 (дельта 0, «без изменений»), но 13 новых и 13 исправленных.
- Исправленные проблемы приходят только при `delta_status=resolved`, у них `runs_in_row` и `first_detected_*` = null.
- Для разбивки по важности и правилам `trend` не приходит; направление «меньше — лучше» следует из
  `higher_is_better: false` у `issues_total` / `critical_issues` в `/api/meta`.

## Q6. Реальные значения и null

| Поле | Наблюдение |
|---|---|
| `actual` | null у 25 из 61 (поле не заполнено), иначе число или строка |
| `expected` | почти всегда строка («сотрудник», «>= 1», «<= 45»), иногда число |
| `owner` | null у 6 из 61 |
| `kr_id`/`kr_title` | null у проблем уровня цели (27 из 61) |
| `goal_level` | в основном `employee` (43), `unit` (15), `hq` (3) |
| Объём | 61 активная + 13 исправленных по блоку; в подразделении до 18 |
| TX-NEW | 0 целей, `clean_goals_share` и тренд — null во всех прогонах |
| TX-SAL | 100 %, 0 проблем, дельта 0 — состояние «всё в порядке» |

## Q7. Необязательные эндпоинты

| Эндпоинт | Ценность для задач пользователя |
|---|---|
| `/api/kkd/units` | Высокая: где стало хуже (Q2, Q4), кому поручать (Q3) |
| `/api/kkd/trend` | Средняя: устойчивое улучшение или случайность; провал CIB-REG виден как обрыв в последнем прогоне |
| `/api/kkd/issues/export` | Средняя: руководитель поручает исправления — список удобно отправить |
| `/api/goals`, `/api/goals/{id}` | Низкая для экрана ККД: проблемы почти не группируются по целям |
| `POST /api/runs` | Низкая: проверка еженедельная по расписанию, внеплановый запуск — функция администратора |

## Q8. Критерии оценки → чем подтверждать

| Критерий | Подтверждение |
|---|---|
| Иерархия информации | Первым видны вердикт и где хуже; затем что исправлять; детали ниже |
| Честность дельты | База сравнения явно; «лучше/хуже» из `trend`; null ≠ 0; первый прогон без статусов; агрегат не скрывает провалы |
| Работа с параметрами | Смена подразделения/прогона/фильтров без перезагрузки, состояние в URL |
| Граничные состояния | RUN-001, RUN-006, TX-NEW, задержка, сеть, пустой фильтр |
| UI-кит и код | Тема из кита, без hex в компонентах, структура папок, без дублей запросов |

В БТ отдельно: «100% соответствие визуала макетам» — в тестовом макеты заменены `UI-KIT.md`.

## Q9. UI-кит

Тема antd копируется целиком; цвета — только из темы/CSS-переменных; текст 14/22, заголовки 20/600/28;
карточки — радиус 8–16, фон `colorBgContainer` на `colorBgLayout`, граница `colorBorderSecondary`;
модалка — радиус 28; контролы 32px; отступы кратны 4. Раздел 5 прямо подсказывает: цвет дельты — от `trend`,
рядом стрелка и значение; null → «нет данных для сравнения» в `colorTextTertiary`; важность — `Tag` с текстом;
статусы дельты — заданные фоны и подпись словом.

## Q10. Ошибки API

| Запрос | Ответ |
|---|---|
| Неизвестный прогон / подразделение / проблема | 404 `RUN_NOT_FOUND` / `UNIT_NOT_FOUND` / `ISSUE_NOT_FOUND` |
| Упавший прогон (summary, issues, карточка) | 409 `RUN_FAILED`; причина — в `error` из `/api/runs` |
| Недопустимое значение фильтра | 422 `INVALID_PARAM` в едином формате |
| Нарушение границ параметра (`limit=0`) | **422 в формате FastAPI `{"detail": [...]}`, не в едином** — клиент должен это переварить |
| Задержка | 300 мс на каждый `/api/*` |
