# План изучения проблематики

Цель этапа — понять задачу до того, как проектировать экран: кто пользователь, какие решения он принимает
по странице ККД, что на самом деле лежит в данных и по каким критериям будут оценивать результат.
Решение проектируется только после того, как гипотезы проверены на данных.

## 1. Вопросы исследования

| # | Вопрос | Зачем |
|---|---|---|
| Q1 | Кто пользователи страницы и какое решение каждый принимает по итогам еженедельной проверки? | Определяет, что должно быть видно первым |
| Q2 | Что значит «стало лучше / хуже» — по какой метрике, на каком уровне оргструктуры? | Главный вопрос руководителя из задания |
| Q3 | Что значит «что исправлять в первую очередь» — по какому признаку приоритизировать и кому поручать? | Второй главный вопрос из задания |
| Q4 | Как устроены каскад и агрегирование: может ли агрегат по блоку скрывать провал в подразделении? | Риск «зелёного» итога при реальной проблеме |
| Q5 | Как устроена дельта: что такое «та же» проблема, с каким прогоном сравниваем, что при первом и упавшем прогоне? | Критерий «честность отображения дельты» |
| Q6 | Какие значения реально приходят в каждом демо-сценарии, какие поля бывают null, какие объёмы данных? | Проектировать под реальные данные, а не под пример из README |
| Q7 | Какие эндпоинты кроме обязательных дают ценность для двух главных вопросов? | Не упустить полезные данные, не тащить лишние |
| Q8 | По каким критериям оценивается работа, и чем подтвердить выполнение каждого? | Приоритеты работ |
| Q9 | Что требует UI-кит (токены, подсказки по экрану ККД, чек-лист)? | Соответствие визуалу |
| Q10 | Какие граничные состояния и ошибки реально отдаёт API? | Поведение интерфейса в граничных случаях |

## 2. Источники

1. Задание Frontend (PDF) — требования и критерии оценки.
2. БТ «Трекер целей» (PDF со sberdisk) — исходная постановка заказчика, целевая аудитория, критерии приёмки.
3. Задания BA, SA, Backend (PDF со sberdisk) — та же предметная область с других сторон: user stories, правила,
   метрики, контракт, семантика дельты.
4. Репозиторий mock API: README, UI-KIT.md, исходный код (`catalog.py`, `engine.py`, `store.py`, `main.py`).
5. Живой mock API — фактические ответы по всем демо-сценариям.

## 3. Методы

| Метод | Что даёт | Вопросы |
|---|---|---|
| Сопоставление пяти документов кейса: роли, user stories, критерии | Портрет пользователя и его решений | Q1–Q3, Q8 |
| Чтение исходного кода mock API | Точная семантика метрик, дельты, каскада, null | Q4, Q5, Q10 |
| Выгрузка ответов API по матрице «подразделение × прогон» скриптом | Реальные значения, распределения, граничные случаи | Q2–Q4, Q6, Q7, Q10 |
| Проверка ошибок: несуществующие прогон/подразделение, неверные параметры, упавший прогон | Коды и тексты ошибок | Q10 |
| Разбор UI-KIT.md по разделам | Требования к визуалу | Q9 |
| Формулировка гипотез и проверка каждой на данных | Подтверждённые выводы для дизайна | все |

## 4. Матрица выгрузки данных

- Подразделения: все 13 из `/api/meta`.
- Прогоны: RUN-001 (первый), RUN-005, RUN-006 (упавший), RUN-007 (сравнение через пропуск), RUN-008 (последний).
- Эндпоинты: `summary`, `units`, `issues` (с фильтрами и без), `issues/{id}`, `trend`, `goals`, `runs`.
- Ошибки: `run_id=RUN-999`, `unit_id=XXX`, `severity=bogus`, `run_id=RUN-006`.

## 5. Результаты этапа

1. `02-findings.md` — факты по каждому вопросу Q1–Q10 со ссылкой на источник.
2. `03-hypotheses.md` — гипотезы, как проверялись, вердикт (подтверждена / опровергнута / частично).
3. `04-solution-plan.md` — план решения на основе подтверждённых выводов и сравнение с текущей реализацией.

## 6. Критерий завершения

На каждый вопрос Q1–Q10 есть ответ, подкреплённый документом или данными API. Каждая гипотеза, влияющая на экран,
проверена на данных. Только после этого — план решения.
